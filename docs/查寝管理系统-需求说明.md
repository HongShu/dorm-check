# 学生查寝管理系统 - 需求说明文档

> 本文档用于交付给 AI 编码工具（如 Cursor、Claude Code、v0 等）进行开发。
> 文档遵循"先讲清楚做什么、再讲清楚怎么做、最后讲清楚不要做什么"的结构。

---

## 一、项目背景与目标

### 1.1 业务背景

学校对在校学生执行夜间查寝制度。每晚由宿管对所负责楼栋的每个寝室进行核查，确认应在校的学生是否真的在寝室。

学生的"在校状态"（在校 / 离校）由辅导员在另一套系统中维护，本系统**不负责状态变更**，只负责**查寝核查**与**异常汇报**。

### 1.2 项目目标

构建一个轻量的查寝管理系统，实现：

1. 宿管在手机端**极简、快速地完成**每晚查寝录入
2. 系统**自动判定异常**（应在未在 / 应离已返）
3. 查寝结束后**调用大语言模型生成自然语言简报**给管理员

### 1.3 规模估算

- 学生总数：约 1000-1500 人
- 楼栋数：5 栋
- 寝室数：约 250-300 间
- 宿管：5 人（每人负责 1 栋楼）
- 管理员：1-3 人
- 辅导员：5-10 人（**只读取数据，不操作本系统**）

### 1.4 设计原则

- **极简优先**：宿管端 90% 的操作应该是"看一眼，点提交"
- **正常路径零摩擦**：默认全员在寝，宿管只标异常
- **大模型只在简报环节出现**：不要为了用 AI 而用 AI

## 三、数据模型

### 3.1 学生表 students

来源：从现有 Excel 导入。**字段命名严格按以下定义**。

| 字段名 | 类型 | 说明 | 示例 |
|--------|------|------|------|
| student_id | TEXT (主键) | 学号 | "2481355" |
| name | TEXT | 姓名 | "李旭" |
| gender | TEXT | 性别 | "男" / "女" |
| class_name | TEXT | 行政班 | "电商2401" |
| counselor | TEXT | 辅导员姓名 | "陈果" |
| building | INTEGER | 入住楼栋 | 7 / 10 / 11 / 17 / 19 |
| room | TEXT | 寝室号（用 TEXT 防止丢前导零） | "203" |
| status | TEXT | 在校状态 | "在校" / "离校" |
| updated_at | TIMESTAMP | 状态最后更新时间 | |

### 3.2 查寝记录表 check_records

每晚每个学生一条记录。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| id | INTEGER (自增主键) | |
| check_date | DATE | 查寝日期，例 "2025-04-30" |
| building | INTEGER | 楼栋 |
| room | TEXT | 寝室号 |
| student_id | TEXT (外键) | 学号 |
| status_snapshot | TEXT | 查寝时该生在校状态（提交时冻结） |
| is_present | BOOLEAN | 宿管标记的实际在寝情况 |
| anomaly_type | TEXT | NULL / "应在未在" / "应离已返" |
| checker | TEXT | 查寝人姓名/账号 |
| submitted_at | TIMESTAMP | 提交时间 |

**唯一约束**：`(check_date, student_id)` 组合唯一——同一天对同一学生只保留最新一条记录（覆盖式提交）。

### 3.3 用户表 users

| 字段名 | 类型 | 说明 |
|--------|------|------|
| username | TEXT (主键) | 登录名 |
| password_hash | TEXT | 密码哈希 |
| role | TEXT | "checker" / "admin" |
| name | TEXT | 真实姓名 |
| assigned_building | INTEGER | 仅 checker 角色填写，负责的楼栋号 |

### 3.4 异常判定逻辑（代码层规则，不依赖模型）

提交查寝记录时，根据以下规则自动写入 `anomaly_type`：

```
if status_snapshot == "在校" and is_present == false:
    anomaly_type = "应在未在"     # 失联预警
elif status_snapshot == "离校" and is_present == true:
    anomaly_type = "应离已返"     # 已返校未报备
else:
    anomaly_type = NULL           # 正常
```

## 四、功能需求详细说明

### 4.1 数据初始化

**[功能编号 F-01]** 从 Excel 导入学生数据

- 提供一个一次性脚本或管理员页面，可上传 Excel 文件
- 字段映射参考第 3.1 节
- Excel 列名可能为中文（学号 / 姓名 / 性别 / 行政班 / 辅导员 / 入住楼栋 / 寝室号 / 在校状态），需做映射
- 重复学号采用"覆盖更新"策略
- 导入完成后展示总条数和按楼栋分布

**[功能编号 F-02]** 学生数据每日同步（**第一版可手动，第二版再做自动**）

- 第一版：管理员每天手动上传一次最新 Excel
- 第二版：定时任务从外部数据源拉取（接口待定）

### 4.2 用户登录

**[功能编号 F-03]** 简单登录

- 用户名 + 密码登录
- 登录后根据 role 跳转：checker → 查寝主页；admin → 管理员 dashboard
- 不需要短信验证、SSO 等复杂机制
- 第一版账号由开发者后台手动录入

### 4.3 宿管端

**[功能编号 F-04]** 楼栋寝室列表页

宿管登录后看到的主页面：

```
[页面标题] 7 号楼 - 2025-04-30 查寝

[进度条] 已完成: 12 / 53 个寝室

[寝室列表，按寝室号排序]
✓ 201 已查 (4/4 在寝)
⚠ 202 已查 (3/4 在寝, 1 异常)
○ 203 未查 (4 人应在校)
○ 205 未查 (4 人应在校)
...

[底部按钮] 一键完成今晚查寝
```

要求：
- 寝室卡片显示：寝室号、状态图标、应在校人数、异常数（若有）
- 点击未查寝室进入 F-05 录入页
- 点击已查寝室进入查看/修改模式
- "一键完成今晚查寝"按钮：仅当所有寝室都已查时可点击，点击后触发 F-08 简报生成

**[功能编号 F-05]** 单寝室查寝录入页

```
[页面标题] 7 号楼 203 寝室

[应在校学生区]
4 人应在寝室：
☑ 张三  2480592
☑ 李四  2480623
☑ 王五  2480624
☑ 赵六  2483158

[主按钮，最大、最显眼]
全员在寝，提交

[次要按钮，小字]
有人不在 →（点击后才能取消勾选）
```

**关键交互**：
- **默认所有学生勾选**（=在寝）
- 主按钮"全员在寝，提交"——一次点击即可完成 90% 的寝室
- "有人不在"按钮点击后，勾选框变为可取消状态，并出现"提交异常"按钮
- 提交后返回 F-04，对应寝室卡片状态变为"已查"

**[功能编号 F-06]** 添加返校未报备学生（异常情况）

如果宿管发现某个**系统显示离校**的学生其实在寝室：

- 在 F-05 页底部提供"添加返校学生"入口
- 点击后弹出搜索框，按学号或姓名搜索本寝室"离校"状态的学生
- 选中后该学生作为 `应离已返` 异常加入提交记录

### 4.4 管理员端

**[功能编号 F-07]** 管理员 Dashboard

```
[页面标题] 查寝管理 - 2025-04-30

[查寝进度]
4 / 5 栋已完成
- 7 号楼 ✓ 完成于 21:35
- 10 号楼 ✓ 完成于 21:42
- 11 号楼 ✓ 完成于 21:18
- 17 号楼 ✓ 完成于 21:50
- 19 号楼 ⏳ 进行中 (15/22)

[今日异常] 14 例
- 应在未在: 9 例（疑似失联）
- 应离已返: 5 例（已返校未报备）

[操作区]
[查看简报] [查看异常明细] [导出今日记录]
```

**[功能编号 F-08]** 简报生成与展示

触发时机：
- 自动触发：所有楼栋查寝完成时
- 手动触发：管理员点击"重新生成简报"

实现：调用 LLM API（Claude Haiku / GPT-4o-mini 任选），prompt 模板见第 5 节。

展示：
```
[页面标题] 2025-04-30 查寝简报

[模型生成的自然语言段落，约 200-400 字]

[操作按钮]
[复制] [导出] [重新生成]
```

**[功能编号 F-09]** 异常明细表格

可按以下维度筛选：
- 楼栋
- 异常类型
- 辅导员

字段：日期、楼栋、寝室、学号、姓名、辅导员、异常类型、宿管、提交时间。

支持导出 Excel。

### 4.5 兜底与错误处理

**[功能编号 F-10]** LLM 调用失败兜底

- 模型 API 调用超时或返回异常时，**不能阻塞主流程**
- 兜底显示：原始结构化异常列表（按辅导员分组的纯文本）+ 提示"AI 简报生成失败，以下是原始数据"

**[功能编号 F-11]** 重复提交处理

- 宿管在 22:30 之前可以重新提交某个寝室，覆盖原记录
- 22:30 之后该寝室记录锁定，需管理员介入

**[功能编号 F-12]** 数据缺失处理

- 学生表中楼栋或寝室号为空的学生：导入时单独标记为"未分配"，不参与查寝
- 提交查寝时如果某学生已被改为"离校"但仍出现在应在校列表：以提交那一刻的 status 为准（snapshot 设计）

```
你是宿舍查寝管理系统的助手。以下是 {date} 全部楼栋查寝完成后的异常情况：

- 10号楼 514 徐子翔 (辅导员: 王悦)
- 11号楼 418 屈静维 (辅导员: 汪财源)

1. 先讲失联风险类，按辅导员归类，方便联系
2. 再讲已返校待更新类
3. 总字数控制在 300 字以内
```

**API 参数建议**：
- model: claude-haiku-4-5 / gpt-4o-mini
- max_tokens: 600
- temperature: 0.3（追求稳定输出）

## 六、技术栈与架构（**锁定**）

> 本节为强约束，开发工具不要替换以下技术选型。

### 6.1 技术栈

- **后端**：Python 3.10+ / FastAPI / SQLAlchemy / Pydantic
- **数据库**：SQLite（单文件，路径 `backend/data/dorm.db`）
- **前端**：微信小程序（原生小程序框架，不用 uni-app / Taro 等跨端方案）
- **LLM**：Anthropic Claude API，模型 `claude-haiku-4-5`
- **部署**：单台 Linux 服务器 + Nginx 反代 + uvicorn / gunicorn

## 七、UI/UX 关键约束

1. **宿管端必须移动优先**，按钮足够大，单手可操作
2. **关键按钮颜色突出**：F-05 的"全员在寝，提交"应为系统主色（如蓝色或绿色），占满宽度
3. **不要任何不必要的动画**，宿管在赶时间
4. **错误提示明确**：不要"操作失败"这种模糊文案，要"网络断开，请检查 WiFi 后重试"
5. **管理员端可以桌面优先**，因为通常在办公室操作

## 八、开发分阶段建议

### 阶段一（第 1 周）：后端 + 数据
- 数据库 schema
- Excel 导入功能

### 阶段二（第 2 周）：宿管端
- 登录页
- 楼栋寝室列表页
- 单寝室查寝页
- 真机测试一次完整查寝流程

## 九、明确不做的事（避免范围蔓延）

6. ❌ 数据可视化图表（柱状图、趋势图等）

8. ❌ 多学期/多学年的归档管理
9. ❌ 复杂权限系统（部门、角色继承等）
10. ❌ 离线录入（必须有网才能查寝）

这些功能**留待后续版本**根据实际使用情况再评估。

## 十二、给 AI 编码工具的使用指引

> 本节是对 AI 工具（Cursor / Claude Code / v0 等）的元指令，请在开始编码前阅读。

### 12.1 阅读顺序

1. 先读第一节理解业务背景
2. 再读第三节理解数据模型——**所有字段命名严格按 3.1-3.3 节，不要自行改名**
3. 然后读第四节功能需求——**所有页面交互严格按 F-04、F-05 描述实现**
4. 第五节 prompt 模板**直接复制使用**，不要"优化"
5. 第六节技术栈**强约束，不要替换**
6. 第九节"明确不做的事"**绝对不要主动添加这些功能**

### 12.2 开发交互模式

**分阶段交付**：按第八节阶段一/二/三分别开发，每完成一个阶段先和用户确认再进入下一阶段。

**单次任务粒度**：用户每次只让你做"一个阶段中的一部分"，不要一次性产出整个项目的全部代码。

**功能编号沟通**：用户提到"F-05 这里调整一下"时，直接定位到第四节对应章节，不要让用户重复描述。

### 12.3 必须遵守的红线

1. ❌ **不要**把 SQLite 替换成 MySQL/PostgreSQL，即使你觉得"更专业"
2. ❌ **不要**把小程序替换成 React/Vue Web 应用
3. ❌ **不要**给 LLM prompt 加"思维链"、"自我反思"等花哨提示工程
4. ❌ **不要**自动添加用户头像、消息中心、通知系统等"标配功能"
5. ❌ **不要**把异常判定逻辑交给 LLM 处理——**异常判定永远是代码规则**，LLM **只**负责生成简报文本
6. ❌ **不要**为了"更好的体验"添加大量动画、过渡效果
7. ❌ **不要**自行设计复杂权限系统（RBAC、ABAC 等）

### 12.4 遇到不明确的需求时

- **不要自行假设**，停下来问用户
- 提问格式：明确指出文档第几节第几条不清晰，给出 2-3 个可能的解读，让用户选
- 例：「文档 4.3 节 F-06 提到"添加返校学生"，但没说明添加后是否需要二次确认。我倾向于不需要确认（保持极简），但也可以加一个 toast 提示。请确认：A) 不确认；B) 加 toast；C) 弹窗确认。」

### 12.5 第一次启动时的建议指令

用户第一次和你对话时可能会说"按这个文档开始开发"。建议你这样回应：

> 我已读完需求文档。按文档第八节，我从阶段一开始：
> 1. 创建项目骨架（按 6.3 项目结构）
> 2. 初始化 SQLite 数据库 + SQLAlchemy 模型（按 3.1-3.3）
> 3. 实现 Excel 导入（F-01）
> 4. 实现登录 API（F-03）
>
> 这一步预计产出：可运行的后端项目 + 一个能跑的导入脚本。
> 完成后我会给你接口测试方法，请确认后我开始？

不要一上来就闷头写一万行代码。
